## Reste à faire

`API-212` **Retoucher un parcours existant : viser une distance, déplacer l'arrivée (L, mesure d'abord)** — 
le générateur de parcours (`RouteGeneratorService`, moteur osm-route-details) part toujours de
zéro : rallonger ou raccourcir un parcours enregistré, ou en changer l'arrivée, ne se fait qu'à la
main dans le planificateur, point de passage par point de passage. Proposition : une **greffe
locale** dans le moteur (un tronçon remplacé, le reste rendu dans sa géométrie d'origine), posée
sur le document `network_edges` du parcours, avec deux opérations — viser une distance (la
recherche d'aller simple existante entre deux coutures, arêtes gardées interdites) et déplacer
l'arrivée ou le départ (un arbre depuis le nouveau point, le parcours quitté là où abandon et
raccord coûtent le moins) —, un endpoint `POST /v1/generator/routes/edit` côté moteur, un endpoint
par parcours côté backend, et deux actions sur la page d'un parcours du site, dont le résultat
s'ouvre dans le planificateur sans rien écraser. Décidé le 22 novembre 2026 (plan §9) : tout parcours enregistré ayant ses
`network_edges`, refus et renvoi au générateur au-delà d'environ ±30 %, tronçon choisi par le
moteur, arrivée sur la carte ou sur un lieu de l'équipe ; déplacer le départ et l'enregistrement
direct sont écartés de la première version. Rien n'est codé. Le lot 0 est une mesure, dans
osm-route-details : la continuité de l'appariement le long d'un parcours n'est pas connue.
