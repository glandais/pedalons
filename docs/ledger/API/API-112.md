## Livré

`API-112` **Fusionner plusieurs GPX en un seul tracé** (2026-10-15, **API 11.2.0**, pas de migration) — `POST /api/gpx-previews/merge` (multipart `gpxFiles`, `@RolesAllowed("user")`, 201 + `GpxPreviewDto`). Bornes : 2 à 10 fichiers (`GPX_MERGE_FILE_COUNT`, nouveau), aucun fichier → `FILE_REQUIRED` ; chaque fichier ≤ 10 Mo **et leur somme ≤ `GpxLimits.MAX_MERGE_TOTAL_BYTES` = `MAX_GPX_SIZE_BYTES`** (`FILE_TOO_LARGE`, vérifiée avant toute lecture) ; chaque fichier passe `parseGpx` et son plafond de distance, puis le document fusionné, liaisons comprises, repasse `GpxLimits.checkTracks` (`GPX_TOO_LONG`) ; un fichier sans aucun point refuse toute la fusion (`GPX_EMPTY`). `service/gpx/GpxTrackMerger` (classe pure) : chaque `trk`/`rte` non vide est une pièce (ses `trkseg` restent ensemble), 16 pièces au plus (`GPX_MERGE_TOO_MANY_TRACKS`, nouveau) ; l'ordre **et** le sens de chaque pièce sont choisis par programmation dynamique exacte sur (sous-ensemble, dernière pièce, sens), O(2ⁿ·n²), pour minimiser la somme des distances haversine fin → début ; pièce 0 toujours à l'endroit, et à coût égal l'indice le plus bas et l'endroit l'emportent, si bien que des fichiers déjà en ordre ressortent inchangés. Sortie : une trace, un `trkseg`, pièces retournées inversées, point en double retiré sous 1 m, sinon liaison droite comptée dans la distance ; waypoints réunis sans doublon exact. Nom : les noms des fichiers (ou leur nom de fichier sans `.gpx`) joints par « + », dans l'ordre d'envoi. Le document passe ensuite par `GpxPreviewService.create(GpxDocument, name)`, même pipeline qu'un dépôt. La haversine de `GpxLimits` devient `common.GeoDistance`. L'interface est `WEB-87`. Tests (verts le 15 octobre 2026) : `GpxTrackMergerTest` (dont la comparaison à une recherche exhaustive sur 40 cas aléatoires), `GpxPreviewResourceTest.mergePreviews_*`, `GpxLimitsResourceTest.mergePreviews_*` (fichier trop gros, somme trop grosse, trace trop longue). **À ne pas défaire** : la DP exacte — pas d'heuristique gloutonne, et pas plus de 16 pièces sans la remplacer (chaque pièce double temps et mémoire) ; l'inversion des pièces fait partie de l'optimum ; bornes 2..10 fichiers ; la somme des tailles bornée comme un seul dépôt (`SEC-6` : la borne de distance ne limite que la sortie rééchantillonnée, pas les points bruts), ce qui laisse aussi la requête loin du `max-body-size` de 100 Mo et de son 413 nu.
