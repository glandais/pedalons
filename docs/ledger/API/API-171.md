## Livré

`API-171` **Changement de groupe en un appel** (2026-11-10, **contrat `13.5.0`**, nouvel endpoint ; aucune migration) — pour `MOB-134`. Changer de groupe était quitter puis rejoindre, deux appels : si le second échouait, la personne n'était plus inscrite nulle part. `POST /api/teams/{teamSlug}/rides/{rideSlug}/groups/{groupId}/switch` → `RideParticipationDto`, 201 quand l'inscription change, 200 quand c'est déjà ce groupe (rien ne change, personne n'est prévenu) ; `NOT_REGISTERED` (400) sans inscription dans la sortie, 404 pour un groupe d'une autre sortie, `GROUP_FULL` ou `RIDE_PAST` (409) en laissant l'inscription où elle était. `RideService.switchGroup` : une transaction, le même verrou (`lockForJoin`) et les mêmes contrôles que `joinGroup` ; l'ancienne inscription est supprimée et une nouvelle écrite, si bien que l'organisation reçoit un seul « a rejoint le groupe … » qui nomme le nouveau groupe ; le résultat sort du paquet service par `RideSwitchAnswer`. Tests qui couvrent : `RideServiceTest` (`switchGroup_…`, sept cas), `RideResourceTest.switchGroup_refusals_shouldLeaveTheRegistrationWhereItWas`, `RideSwitchGroupRaceTest` (`aSwitchAndAJoinForTheLastSeat_shouldFillItOnce`, `twoSwitchesOfOnePerson_shouldLeaveOneRegistration`). **À ne pas défaire** : un refus annule tout, jamais une inscription perdue.
