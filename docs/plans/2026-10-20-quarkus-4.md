# Passer le backend à Quarkus 4 et Jackson 3

Écrit le 20 octobre 2026, sur la branche `chore/quarkus-4`. **État : exécuté sur
`4.0.0.Beta1`, la suite backend complète est verte (4 112 tests) ; il reste à suivre la bêta
jusqu'à la version finale** (prévue fin novembre 2026), ledger `API-135`. Ledger `API-133`
(retrait de hypersistence-utils) et `API-134` (Quarkus 4 + Jackson 3) pour ce qui est livré.
Les chemins Java sont relatifs à `backend/src/main/java/fr/pedalons/`.

Sources : [l'annonce de la 4.0.0.Beta1](https://quarkus.io/blog/quarkus-4-0-0-beta1-released/)
et le [guide de migration 4.0](https://github.com/quarkusio/quarkus/wiki/Migration-Guide-4.0),
lus le 20 octobre 2026.

## 1. En une page

Quarkus 4 apporte Hibernate ORM 8 (Jakarta Persistence 4), Jackson 3, Vert.x 5 / Netty 4.2,
Jakarta REST 4 et CDI 5, avec Java 21 au minimum (nous sommes en Java 25, la version recommandée)
et PostgreSQL 16 au minimum par défaut (nous sommes en 17).

Pour nous, le gros du chantier n'était pas Quarkus mais **trois dépendances tierces et Jackson 3** :

| Bloqueur | Pourquoi | Levé par |
|---|---|---|
| `hypersistence-utils-hibernate-71` | pas de module Hibernate ORM 8 | notre propre `@Tsid` et le JSON natif d'Hibernate (§4) |
| `quarkus-amazon-services` | pas de BOM plateforme 4.x | la `4.0.0.Beta3` Quarkiverse, qui vise Quarkus 4.0.0.Beta1 (§5) |
| `geolatte-geojson` 1.11 | module Jackson 2 seulement | `geolatte-geojson-jackson3` 2.0.1 (§5) |
| notre code (48 fichiers) | Quarkus 4 ne produit plus de bean `ObjectMapper` Jackson 2 : ArC échouait sur 22 points d'injection | migration vers `tools.jackson.*` (§6) |

Contrainte qui a guidé chaque arbitrage : **les déploiements sont roulants**. Pendant environ une
minute, l'ancienne version (Quarkus 3.40, Jackson 2) et la nouvelle partagent la base. Le JSON
stocké en JSONB doit donc rester identique à l'octet près, et le JSON de l'API REST aussi, puisque
les clients web et mobile déjà déployés le lisent. Le contrat OpenAPI n'a pas changé
(`pedalons.api.version` non bumpé) et il n'y a aucune migration Flyway.

## 2. Ce que Quarkus 4 change pour nous

Lu dans le guide de migration et confronté au code :

- **Sans effet** : aucune des API Hibernate supprimées (`QueryHints`, `org.hibernate.transform`,
  `@GenericGenerator`, `Session.replicate()`) n'est utilisée ; pas de `@DefaultBean`, pas de
  `SseEventSink`, pas de gRPC, pas d'OIDC ; `quarkus-junit` et `quarkus-junit-mockito` portaient
  déjà leurs nouveaux noms.
- **Jackson 3** : nouveaux paquets `tools.jackson.*` (les annotations restent dans
  `com.fasterxml.jackson.annotation`), `ObjectMapperCustomizer` devient
  `JsonMapperBuilderCustomizer`, et plusieurs défauts changent (§6).
- **Hibernate 8** : `java.time` passe directement par JDBC et le flush est piloté par un graphe.
  La suite complète passe sans réglage ; ni `hibernate.type.java_time_use_direct_jdbc` ni
  `hibernate.flush.queue.type=legacy` n'ont été nécessaires.
- **Micrometer, client Prometheus 1.x** : certaines métriques sont renommées (par exemple
  `jvm_info_total` → `jvm_total`). Les tableaux de bord et alertes de la pile de supervision qui
  les lisent sont **à vérifier** au déploiement (§9).
- **HTTP** : le `;` ne sépare plus les paramètres de requête. Aucun de nos clients ne s'en sert.

## 3. Les dépendances tierces qui bloquaient

État vérifié sur Maven Central le 20 octobre 2026 :

- **hypersistence-utils** : modules `-hibernate-71` et `-73` seulement, rien pour Hibernate 8.
  La bibliothèque `io.hypersistence:hypersistence-tsid`, elle, ne dépend pas d'Hibernate et reste.
- **quarkus-amazon-services** : `io.quarkus.platform:quarkus-amazon-services-bom` n'existe pas
  encore en 4.x, mais Quarkiverse publie `io.quarkiverse.amazonservices:quarkus-amazon-services-bom`
  `4.0.0.Beta3` (17 octobre), construit contre Quarkus `4.0.0.Beta1` et le SDK AWS 2.55.10.
- **geolatte** : la version 2.0 éclate l'artefact en `geolatte-geojson-core`,
  `geolatte-geojson-jackson2` et `geolatte-geojson-jackson3`. Le module Jackson 3 est
  `org.geolatte.geom.json.jackson3.GeolatteGeomModule`.

## 4. Étape 1 — se passer de hypersistence-utils (`API-133`)

Faite d'abord sur Quarkus 3.40 / Hibernate 7.4, pour que le remplacement soit vérifiable à
comportement constant (suite complète verte avant le passage à Quarkus 4).

### Les identifiants

`@Tsid` est désormais `infrastructure.hibernate.Tsid`, un `@IdGeneratorType(TsidGenerator.class)`.
`TsidGenerator` implémente `BeforeExecutionGenerator` (API présente à l'identique dans Hibernate
8.0) et reproduit exactement le comportement par défaut de hypersistence, lu dans ses sources
3.16.0 :

- **une seule fabrique par JVM** pour toutes les entités :
  `TSID.Factory.builder().withRandomFunction(TSID.Factory.THREAD_LOCAL_RANDOM_FUNCTION).build()` ;
- 10 bits de nœud, **tirés au hasard au démarrage** sauf si `TSID_NODE` / `tsid.node` est fixé —
  ce n'est le cas nulle part, ni avant ni après ; le risque de collision entre deux instances d'un
  déploiement roulant est donc celui qui existait déjà ;
- 12 bits de compteur, époque au 1er janvier 2020, identifiants strictement croissants dans une JVM.

Seuls les imports des 38 entités ont changé.

### Les colonnes JSONB

Les 19 colonnes passent de `@Type(JsonBinaryType.class)` à `@JdbcTypeCode(SqlTypes.JSON)`, le JSON
natif d'Hibernate. Le `FormatMapper` du PU, `infrastructure.hibernate.JsonbFormatMapper`
(`@JsonFormat @PersistenceUnitExtension`), délègue à `infrastructure.hibernate.JsonbMapper`,
**le seul `ObjectMapper` des colonnes JSONB**. Ce n'est jamais celui de l'API REST, qui omet les
nulls.

`JsonbMapper` reproduit le mapper de hypersistence : nulls écrits, `Instant` en secondes
décimales, propriété inconnue refusée (les documents stockés portent
`@JsonIgnoreProperties(ignoreUnknown = true)`), `OffsetDateTime` en ISO par un (dé)sérialiseur
dédié.

Les champs `JsonNode` portent `@Mutability(JsonNodeMutabilityPlan.class)` : la copie par
aller-retour JSON qu'Hibernate fait par défaut change un `LongNode` en `IntNode`, le nœud ne
compare plus égal à son instantané et la ligne serait réécrite à chaque flush.

Une alternative a été écartée : un `UserType` maison, qui aurait demandé soit
`DynamicParameterizedType` (déprécié pour suppression depuis Hibernate 7.0), soit une API
`@Incubating`, et nous aurait laissé une couche JDBC à maintenir.

## 5. Étape 2 — la plateforme 4.0.0.Beta1

Dans `backend/pom.xml` :

- `quarkus.platform.version` passe à `4.0.0.Beta1` ;
- le BOM AWS est importé depuis `io.quarkiverse.amazonservices` en `4.0.0.Beta3` (propriété
  `quarkus-amazon-services.version`), faute de BOM plateforme ;
- `geolatte-geojson` 1.11 est remplacé par `geolatte-geojson-jackson3` 2.0.1.

Le code S3 (`infrastructure/storage/S3StorageService`, `service/gpx/GpxPreviewService`) n'a pas
changé ; il est validé sur MinIO par la suite complète.

## 6. Étape 3 — tout le code en Jackson 3 (`API-134`)

### Correspondance des API

| Jackson 2 | Jackson 3 |
|---|---|
| `com.fasterxml.jackson.databind.*`, `core.*` | `tools.jackson.databind.*`, `tools.jackson.core.*` |
| `JsonProcessingException` (vérifiée) | `JacksonException` (**non vérifiée**) |
| `JsonSerializer` / `JsonDeserializer` / `SerializerProvider` | `ValueSerializer` / `ValueDeserializer` / `SerializationContext` |
| `asText()` / `textValue()` / `isTextual()` | `asString()` / `stringValue()` / `isString()` |
| `JsonParser.getText()` | `getString()` |
| `registerModule(…)`, `findAndRegisterModules()` | builder : `.addModule(…)` (le mapper est immuable) |
| modules `jsr310`, `jdk8`, `parameter-names` | intégrés à databind 3 — retirés du pom |

Les exceptions demandaient un examen au cas par cas plutôt qu'un rechercher-remplacer : un
`catch (IOException)` qui n'entourait que des appels Jackson ne compile plus, et un
`catch (IOException)` qui mêlait I/O et Jackson aurait pu laisser passer une erreur de parsing.
Aucun cas de ce second type n'existait. `BiketeamExportClient` garde sa remontée de causes jusqu'à
`BiketeamJobLostException` : l'`IOException` du flux arrive maintenant enveloppée dans un
`JacksonIOException`.

### Le JSON de l'API REST reste celui de Quarkus 3.40

Propriétés ajoutées dans `application.properties` :

```properties
quarkus.jackson.fail-on-null-for-primitives=false
quarkus.jackson.fail-on-trailing-tokens=false
quarkus.jackson.default-view-inclusion=true
quarkus.jackson.use-getters-as-setters=true
quarkus.jackson.allow-final-fields-as-mutators=true
# activé par défaut en Quarkus 4, éteint en 3.40
quarkus.rest.jackson.optimization.enable-reflection-free-serializers=false
```

`infrastructure/json/PedalonsJacksonConfig` (désormais un `JsonMapperBuilderCustomizer`) enregistre
le module geolatte Jackson 3 et remet les défauts Jackson 2 qui n'ont pas de propriété Quarkus :

- `NON_NULL` sur la valeur **et sur le contenu** — `setDefaultPropertyInclusion(NON_NULL)` de
  Jackson 2 faisait les deux, les valeurs nulles des `Map` disparaissaient aussi ;
- ordre de déclaration des propriétés, pas l'ordre alphabétique de Jackson 3 ;
- enums lus et écrits par `name()`, pas par `toString()` ;
- mois `java.time` comptés à partir de zéro (inerte aujourd'hui : aucun DTO ne porte de `Month`) ;
- zéros de fin des `BigDecimal` d'un arbre retirés (`valueToTree(1.50)` donnait `1.5`) ;
- caractères hors BMP (emojis) échappés en `\uXXXX` dans l'UTF-8, ce qui garde aussi stables les
  octets que hache `WeatherEtag`.

`infrastructure/json/PedalonsJsonFactoryConfig` ramène la profondeur d'imbrication à 1000 (Jackson
2.22) au lieu de 500 (Jackson 3), sans quoi un contexte de retour d'erreur entre 501 et 1000
niveaux serait refusé.

### Les colonnes JSONB restent identiques à l'octet près

Le `JsonMapper.builder()` de `JsonbMapper` rétablit un par un les défauts Jackson 2 que Jackson 3 a
changés : dates et durées en nombres, propriété inconnue refusée, null accepté pour un primitif,
contenu après le document toléré, ordre de déclaration, enums par `name()`, mois à partir de zéro,
`BigDecimal` sans zéros de fin, surrogates non combinés, profondeur 1000. Aucun module n'est
découvert par le classpath, pour qu'un jar ajouté plus tard ne puisse pas changer ce qui est
stocké. Les versions 3.40 et 4 relisent chacune ce qu'écrit l'autre.

### Jackson 2 reste sur le classpath

`timeshape` et `magika` tirent encore `jackson-core` / `jackson-databind` 2.22.2. Ce n'est pas un
problème pour elles, mais un import Jackson 2 oublié dans notre code **compilerait sans erreur** :
d'où la règle ArchUnit du §7. `jackson3.version` reste surchargé à 3.2.3 : `quarkus-bom`
4.0.0.Beta1 fige 3.1.4, en dessous de la 3.2.x contre laquelle webauthn4j 0.31.11 est compilé
(3.2.0 et 3.2.1 ont des avis GHSA).

## 8. Changements de comportement acceptés

Jackson 3 est plus strict sur les nœuds JSON. Ces écarts ne touchent que des réponses tierces
malformées et ont été laissés tels quels :

- `asString()` lève une exception sur un objet ou un tableau (Jackson 2 rendait `""`) ; `asLong()`,
  `asInt()`, `asDouble()` sans défaut lèvent sur une valeur non convertible (Jackson 2 rendait 0).
  Concerne Open-Meteo, FCM et GitHub, toujours dans des blocs qui traitent déjà l'erreur.
- `canConvertToLong()` sur un décimal non entier rend `false` : un `expires_in` OAuth fractionnaire
  (3.7) donne `null` au lieu de 3 dans les clients GPS. OAuth le définit entier.
- `readTree("")` rend un `MissingNode` et non `null`.
- `BiketeamRequestTokenVerifier`, sur les défauts bruts de Jackson 3, refuse désormais du contenu
  après le jeton : plus strict, ce qui convient à un vérificateur. `ValhallaErrors`, lui, a été
  réglé pour continuer de lire un corps suivi de contenu parasite.

Les tests qui créent un `new ObjectMapper()` au lieu du mapper injecté tournent sur les défauts
bruts de Jackson 3 : ils passent, mais ne reflètent pas la configuration de production.

## 9. Ce qui reste (`API-135`)

À faire à la version finale de Quarkus 4 (ou à une CR) :

- revenir au BOM plateforme `io.quarkus.platform:quarkus-amazon-services-bom` ;
- relire les surcharges du pom : `jackson3.version` (à retirer si `quarkus-bom` rattrape la 3.2.x)
  et `log4j-api` 2.26.1, déjà la version du BOM 4.0.0.Beta1, que la règle du commentaire permet de
  retirer ;
- relancer `RestJsonParityTest`, `JsonbMapperTest` et la suite complète.

Points ouverts relevés pendant la migration :

- **Le contrat OpenAPI régénéré change** sous Quarkus 4 (SmallRye OpenAPI, pas Jackson) : le bloc
  `servers` auto-généré (`localhost:8080`, `0.0.0.0:8080`) disparaît, ainsi qu'un `pattern: ""`
  sans effet sur le lien d'un lieu. `contracts/openapi.*` ont été remis à leur état d'avant à
  chaque build ; il faut décider si les clients générés lisent `servers[0]`, ou fixer ces valeurs
  par la configuration `quarkus.smallrye-openapi.*`, avant le premier commit qui régénère le
  contrat.
- **Supervision** : vérifier, sur un `/q/metrics` de la 4, les noms lus par
  `services/monitoring/prometheus/rules/pedalons.yml` (dont `agroal_*` pour
  `BackendConnectionPoolExhausted`, et ses tests `prometheus/tests/pedalons.test.yml`) et par les
  tableaux de bord Grafana (`jvm_*`, `http_server_requests_seconds_*`) : le client Prometheus 1.x
  renomme certaines métriques et les compteurs passent en entiers.
- **GeoJSON** : la sortie de `geolatte-geojson-jackson3` n'est couverte qu'à travers les tests des
  annonces et des lieux ; aucune géométrie n'est comparée octet par octet.
- **Rolling deploy 3.40 → 4** : vérifié par les tests de compatibilité JSON, pas encore par un
  déploiement réel. À observer au premier déploiement. Un retour arrière (4 → 3.40) repose sur la
  même garantie : chaque version relit ce qu'écrit l'autre.
- **La configuration de production n'a pas été passée au crible.** `quarkus update` (les recettes
  OpenRewrite qui renomment la centaine de propriétés supprimées par la 4) n'a pas été lancé, et
  les tests ne voient que `application.properties`, pas les variables d'environnement de
  `docker-compose.yml` / `.env`. Celles-ci sont toutes `QUARKUS_MAILER_*`, dont
  `QUARKUS_MAILER_START_TLS` ; le guide renomme `quarkus.mailer.ssl` en `tls` et envoie
  `trust-all` vers le TLS Registry. Une clé supprimée est **ignorée sans erreur** : vérifier chaque
  clé contre la configuration du mailer de la 4, puis lire au démarrage de la pile locale les
  avertissements `Unrecognized configuration key`, avant le premier déploiement. C'est d'autant plus
  important que la règle « une pile locale ne doit pas pouvoir envoyer de mail » repose sur ces
  variables.
- **`quarkus.hibernate-orm.mapping.format.global` est dépréciée en 4** : avertissement au build
  (`Deprecated configuration property … should not be used anymore`). Elle reste pour l'instant
  (voir §10) ; à la version finale, trouver ce qui la remplace, la retirer et vérifier avec
  `JsonbMappingTest` que les colonnes passent toujours par `JsonbFormatMapper`.

## 10. À ne pas défaire

- Jamais l'`ObjectMapper` de Quarkus/REST sur une colonne JSONB. Ne toucher à la configuration de
  `JsonbMapper` qu'avec `JsonbMapperTest` vert, sans modifier son document de référence.
- Ne retirer aucune des propriétés `quarkus.jackson.*` ci-dessus, ni
  `enable-reflection-free-serializers=false`, ni un réglage de `PedalonsJacksonConfig` ou de
  `PedalonsJsonFactoryConfig`, sans `RestJsonParityTest` vert.
- `NON_NULL` porte sur la valeur **et** le contenu.
- Aucun import Jackson 2 : la règle `no_jackson_2` reste.
- Une seule fabrique TSID pour toutes les entités, nœud aléatoire par JVM.
- `@Mutability(JsonNodeMutabilityPlan.class)` sur tout champ `JsonNode` mappé en JSON.
- `quarkus.hibernate-orm.mapping.format.global=ignore` reste, malgré sa dépréciation en 4, tant
  que son remplaçant n'est pas identifié (§9).
- `JsonbFormatMapper` reste non `final` et sans scope explicite : ses annotations Quarkus en font
  un bean `@ApplicationScoped`, et un bean perdu ferait retomber Hibernate **sans bruit** sur son
  mapper par défaut. `TsidGenerator`, à l'inverse, n'est **pas** un bean CDI : Hibernate
  l'instancie par son constructeur sans argument, comme il le faisait pour celui de hypersistence.
- `TSID.Factory.getTsid()`, dans les services et dépôts qui fabriquent un identifiant à la main
  (insertions natives, identifiants de fichiers : `ThumbnailService`, `AssetService`,
  `GpxPreviewService`, `PushDeviceRepository`, `ContentReportRepository`…), utilise **une autre
  fabrique** que `@Tsid` : celle par défaut de la bibliothèque, sur `SecureRandom`, avec son propre
  nœud aléatoire. C'était déjà le cas avec hypersistence ; ne pas « unifier » les deux sans peser
  le risque de collision, qui ne change pas tant que chaque fabrique a un nœud aléatoire.
- Les surcharges de version du pom (`jackson3.version`, `log4j-api`) ne jouent que parce que le
  BOM `tools.jackson:jackson-bom` est importé **avant** `quarkus-bom` : le premier BOM importé
  l'emporte.
